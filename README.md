# koshien-scraper

甲子園(春の選抜 / 夏の選手権)の**本大会**の出場校・試合結果を収集し、
PostgreSQL(Supabase)へ取り込むためのスクレイパ。

対象期間: **1978年(1県1代表化)以降**
対象大会: 春の選抜、夏の選手権(いずれも甲子園本大会のみ。地方大会は対象外)

---

## 1. 取得元の選定

候補を実地に確認した結果を記す。

| 候補 | 内容 | 判定 |
|------|------|------|
| **Wikipedia 日本語版** | 大会ごとに独立記事。出場校表と全試合結果を掲載。MediaWiki APIあり | **採用** |
| 日本高等学校野球連盟 (jhbf.or.jp) | 公式。ただし過去大会は「大会小史」中心で全試合結果は非掲載 | 突合用の参照に留める |
| 阪神甲子園球場 (koshien.hanshin.co.jp) | 過去大会ページあり。直近十数年に限られる | 補助 |
| やっぱり甲子園 (hsbb.jp) | 構造が理想的だが **robots.txt が自動アクセスを禁止** (アクセス試行で確認) | **除外** |
| 高校野球ドットコム (hb-nippon.com) | 記事URLが不安定(404)。二次利用条件も不明確 | 除外 |
| 個人運営のデータサイト各種 | 網羅性は高いが規約が不明。個人サーバへの負荷も懸念 | 除外 |

### Wikipedia を選ぶ理由

- 1978年以降のすべての大会に記事が存在する
- **MediaWiki API** が公開されており、HTMLの力任せな取得より軽く、構造も安定
- 内容が **CC BY-SA 4.0**。スコアなどの事実データ自体に著作権は及ばないが、
  記事由来であることを明示できる形(出典URL + `oldid`)で保存する
- robots.txt が API 利用を許容している

### 守っている作法

- `User-Agent` に連絡先メールアドレスを必須化(Wikimedia のポリシー)。未設定なら起動時に失敗する
- リクエスト間隔は既定 1 秒。`maxlag=5` を付与し、サーバ遅延時は自動で待つ
- 取得結果は `data/cache/` に保存し、再実行時はネットワークに出ない
- 全大会分でも API 呼び出しは 100 回程度(1978〜2025年の春夏で 95 大会)

## 3. 使い方

Python環境は [uv](https://docs.astral.sh/uv/) で管理する。`uv` があれば
Python本体の用意も仮想環境の作成も不要で、`uv run` が自動で解決する。

```bash
# uv 未導入なら
curl -LsSf https://astral.sh/uv/install.sh | sh

# 依存を uv.lock どおりに再現(.venv が自動生成される)
uv sync
```

`uv sync` はロックファイルに固定されたバージョンをそのまま入れるため、
環境によって挙動が変わらない。CI では `uv sync --frozen` を使い、
`uv.lock` と `pyproject.toml` の齟齬を検出させる。

```bash
# Wikimediaのポリシーにより連絡先入りUAが必須
export KOSHIEN_UA='koshien-db/0.1 (your-name; you@example.com)'

# 1) 記事の存在確認とキャッシュ作成
uv run koshien fetch --from 1978 --to 2025

# 2) パース + 検証 → data/parsed/*.json
uv run koshien parse --from 1978 --to 2025

# 2') パースが空振りしたら実記事の構造をダンプして調査
uv run koshien debug --from 1978 --to 1978 --seasons spring

# 3) 検証のみ再実行(パース結果を直したあとなど)
uv run koshien validate --from 1978 --to 2025 -v

# 4) Supabaseへ投入(まずはドライラン)
export SUPABASE_DSN='postgresql://postgres:PASS@db.xxxx.supabase.co:5432/postgres'
uv run koshien load --from 1978 --to 2025 --dry-run
uv run koshien load --from 1978 --to 2025 --auto-create-schools
```

`koshien` コマンドは `pyproject.toml` の `[project.scripts]` で定義しているため、
`uv sync` 後は `uv run koshien ...` で呼べる(`python -m koshien.cli ...` も可)。

`load` の前に `koshien_schema.sql` を Supabase の SQL Editor で実行しておくこと。
書き込みは RLS を迂回する必要があるため、DSN には接続文字列(サービスロール相当)を使う。

### 開発

```bash
uv run pytest              # 回帰テスト(フィクスチャは自動生成される)
uv run ruff check .        # lint
uv run ruff check --fix .  # 自動修正

uv add <package>           # 依存追加(pyproject.toml と uv.lock を同時更新)
uv add --dev <package>     # 開発用依存の追加
uv lock --upgrade          # 依存の更新
```

`pip install` や `requirements.txt` は使わない。依存の追加は必ず `uv add` で行い、
`uv.lock` をコミットする。

## 4. 書式が2系統ある問題

調査の結果、**大会記事の試合結果は年代によって書式が異なる**ことが分かった。
これが本スクレイパの設計上いちばん重要な点である。

**A. 表形式**(概ね2000年代以降)

| 試合日 | 試合順 | 勝利 | スコア | 敗戦 | 備考 | 試合時間 |
|---|---|---|---|---|---|---|
| 8月13日 (第3日) | 第2試合 | 鹿屋中央 | 2x - 1 | 市和歌山 | 延長12回 | 2時間13分 |

**B. 箇条書き形式**(概ね1990年代以前)

```
8月8日
・仙台育英 1x - 0 高松商(延長17回)
```

`parse.py` は表形式を先に試し、10試合未満しか取れなければ箇条書き形式に切り替える。
どちらの経路でも同じ `GameRow` を返す。

### 共通する制約: 先攻/後攻が分からない

どちらの書式も「勝利校・敗戦校・スコア」であって、先攻/後攻ではない。
そのため **DBスキーマを変更した**。

- `entry1_id` / `entry2_id` … 掲載順の2校(確定試合では `entry1` が勝利校)
- `first_bat_entry_id` … 先攻が判明した場合のみ設定
- 判明するのはサヨナラ勝ち(スコアの `x`)のケース。x が付いた側が後攻と確定できる
- 対戦カードの向きに依存しない一意キーを作るため、生成列 `pair_lo` / `pair_hi` を追加

### ラウンドの決定

見出し(`1回戦` など)があればそれを使う。無い場合(箇条書き形式の記事に多い)は
**トーナメント構造から逆算**する。

```
末尾から   1試合 → 決勝
その前の   2試合 → 準決勝
その前の   4試合 → 準々決勝
その前の   8試合 → 3回戦
その前の  16試合 → 2回戦
残り              → 1回戦
```

49代表なら `17 + 16 + 8 + 4 + 2 + 1 = 48` 試合となり、実データと一致する。
引き分け再試合は同一カードの連続として検出し、1つの枠にまとめて数える。
1978年夏の記事(見出しなし・箇条書き)で、この逆算が正しいラウンド構成を
復元することをテストで確認済み。

## 5. 検証

トーナメントという構造上、機械的に強い検証がかけられる。`validate.py` が以下を確認する。

| 種別 | 内容 |
|------|------|
| error | 試合数 ≠ 出場校数 − 1 (+ 再試合数) |
| error | 試合結果に出場校表へ存在しない学校名が出てくる |
| error | 2敗以上している学校がある |
| error | 無敗の学校がちょうど1校でない(= 優勝校が特定できない) |
| error | 決勝が1試合でない / 準決勝が2試合でない … |
| error | 夏なのに地方大会が空、春なのに地方大会が入っている |
| error | 都道府県が解決できない出場校がある |
| warn | 出場校数が想定レンジ外(夏 47〜60、春 28〜40) |

`parse` はエラーがあっても JSON を書き出したうえで件数を報告する。
**エラーが残っている大会は `load` せず、個別に原因を潰す**運用を前提とする。

## 6. うまく取れないときの調べ方

記事の書式は年によって揺れるため、パースが空振りすることがある。
そのときは `debug` サブコマンドで実記事の構造をダンプする。

```bash
uv run koshien debug --from 2014 --to 2014 --seasons summer
```

見出し一覧、各テーブルのクラス・直前見出し・先頭3行、スコアらしき箇条書きが出力されるので、
**どの表を拾えていないのか**、**列名が想定と違うのか**が一目で分かる。

これまでに判明した、実記事とフィクスチャの差異は以下のとおり(いずれも対応済み)。

| 症状 | 原因 | 対応 |
|------|------|------|
| `no_entries` (出場校0件) | 出場校表の**先頭行が「東日本 / 西日本」の見出し行**で、列名は2行目にあった。ヘッダ行を先頭行決め打ちで読んでいたため全滅した | `_find_header_row()` が先頭4行から列名行を探索する |
| `no_final` / 試合が1件足りない | **決勝が一覧表・箇条書きに含まれず、イニングスコア表だけで掲載**されている | `parse_linescores()` がスコアボードを解析し、一覧から漏れた試合を補完する |

スコアボードの解析には副次的な利点がある。野球の記載慣習で**上段が先攻**なので、
決勝については `first_bat_entry_id` を確実に埋められる。

### 新しい書式に出会ったら

1. `debug` で構造を確認する
2. `tests/make_fixtures.py` にその構造を再現したフィクスチャを追加する
3. パーサを直し、`uv run pytest` で既存の年が壊れていないことを確認する

フィクスチャを先に足すことで、ある年の対応が別の年を壊す事故を防げる。

## 7. 学校の名寄せ

記事中の校名は「大阪桐蔭」「大阪桐蔭高」「大阪桐蔭高等学校」のように揺れ、
さらに旧校名(明徳 → 明徳義塾)や同名校(別県)の問題がある。

1. `normalize_school()` で NFKC 正規化、空白・脚注除去、旧字体の吸収、接尾辞(高/高校/高等学校)の除去
2. **都道府県で絞ったうえで** `schools.name` と `school_aliases.alias` を照合
3. 見つからない場合:
   - `--auto-create-schools` 指定時は新規作成し、記事中の表記を `school_aliases` に登録
   - 未指定時は未解決として記録し、その出場・試合はスキップ

同名校が別県に存在するため、**校名だけで名寄せしない**ことが重要。
初回取り込み後は `school_aliases` を目視で点検し、
別レコードになってしまった同一校を統合する作業が必要になる。

## 8. 既知の限界と今後の作業

| 項目 | 現状 | 対応方針 |
|------|------|----------|
| 21世紀枠の判定 | 春の記事の表構造に依存。列や見出しに「21世紀枠」が無い年は取りこぼす | 春の全年を目視確認し、必要なら年ごとの手動リストで補正 |
| 春の地区 | 記事に地区列が無い場合、都道府県から機械的に補完している | 東京を関東と別扱いにしている点も含め、実際の選出地区と突合 |
| `replay_of_game_id` | 再試合の検出(`replay_seq`)はするが、親試合への紐づけは未設定 | ロード後にSQLで一括更新 |
| 2020年 | 春夏とも中止のため対象外(`titles.CANCELLED`) | 甲子園高校野球交流試合を含めるなら別大会として設計 |
| 記事側の誤り | Wikipedia自体に誤記がありうる | 決勝結果・優勝校は高野連公式の一覧と突合してチェックする |
| 記事書式の揺れ | 年によって表の列名や見出し構成が異なる | `validate` がエラーで検出する。パーサはヘッダ名ベースなので列順の変化には耐える |
| イニングスコア・選手 | 未対応 | `games` の子テーブルとして後日追加(設計ドキュメント §8 参照) |

サンドボックス環境からは `ja.wikipedia.org` へ到達できないため、
**パーサの検証は実記事の構造を再現したフィクスチャで実施している**。
実データでの初回実行時は、まず `--from 2014 --to 2014` のように狭い範囲で
`uv run koshien parse` を走らせ、検証がすべて OK になることを確認してから範囲を広げること。
